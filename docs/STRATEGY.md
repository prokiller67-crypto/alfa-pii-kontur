# План решения Alfa PII Proxy

Проверено 22 сентября 2026 по личному кабинету и официальному онбордингу.

Источники: [задача](https://reg.vibecoding-hackathon.ru/results/data-science),
[онбординг](https://reg.vibecoding-hackathon.ru/ds.pdf),
[финальная сдача](https://reg.vibecoding-hackathon.ru/results/submitsolution).
Оригинал PDF сохранён в `docs/sources/organizer-onboarding.pdf`.

## Что необходимо для сильного результата

1. Пройти оба обязательных допуска: проверку исходников и внешнюю нагрузочную проверку.
2. Доказать качество по всем 17 типам данных, отдельно измерять пропуски и ложные срабатывания.
3. Сохранять контекст и восстанавливать исходные символы, пробелы, регистр и пунктуацию точно.
4. Выдержать 1000 RPS при latency до секунды; 2000 RPS даёт дополнительное преимущество.
5. Показать практическое подключение систем, политики, приватные журналы, ошибки и расширяемость.

Весов критериев, открытого размеченного датасета и точной реализации метрики в прочитанных материалах нет.
95% из ТЗ нельзя приравнивать к результату наших собственных тестов.

## Первый рабочий этап

- FastAPI с точным `POST /process`: `{payload,payload_id}` → `{result}`.
- Правила с контекстом для реквизитов + локальная модель Natasha/Slovnet для ФИО и локаций.
- Выделение фрагментов с координатами, приоритетами и разрешением пересечений.
- Отдельные форматы маски: сохранение пунктуации, типизированные токены, частичное скрытие.
- Хранилище зашифрованных замен с TTL и HMAC-ключами; память для одного локального процесса,
  Redis для нескольких процессов. Никакого переключения фазы простым счётчиком.
- Политики систем, явные отказы, метрики без исходного текста и без идентификаторов в labels.
- Негативные примеры: публичная историческая персона, адрес банка, обычные числа и даты.

## Что проверить до подачи

- Тесты ретраев обоих направлений, конфликта ID, параллельных запросов, истечения TTL,
  недоступного хранилища, изоляции систем, утечки через ошибки валидации и логи.
- Отдельный набор качества, который не использовался при исправлении правил.
- Холодная нагрузка на разные тексты отдельно от повторяемых текстов.
- Большой текст до 100 000 токенов: размер в символах не равен числу токенов.
- Внешний сервер: точные характеристики, длительный прогон, p50/p95/p99 и error rate.
- Веб-интерфейс для демонстрации, презентация, исходники без окружения/моделей/датасетов.

## Вопросы организаторам (подготовлены, не отправлены)

1. Поделитесь, пожалуйста, примерами эталонных масок по категориям и реализацией нормированного
   span-based расстояния Левенштейна: допускаются ли типизированные токены и полное скрытие,
   или нужно точно повторять частичные маски вроде `И. И. И.` / `45** ****56`?
2. Есть ли размеченный dev-набор и веса качества/производительности/оценки жюри?
3. Входит ли текст на 100 000 токенов в нагрузку 1000 RPS и каким токенизатором считается длина?
4. Можно ли передать проверке API key или ограничить доступ по IP проверяющей системы?
5. Гарантируется ли уникальность payload_id между разными прогонами и каков максимальный
   интервал между прямой и обратной проверкой?
