# Ограничение ожидания запросов — 23 сентября 2026

Организаторский клиент ждёт ответ не более 10 секунд и разрешает повтор после
HTTP 429 с `Retry-After`. Ранее один checkout из пула PostgreSQL мог ждать
14 секунд, ещё до исполнения SQL. В контрольном внешнем прогоне на старой
версии 8 запросов превысили клиентский таймаут, 184 дали HTTP 200; точно
восстановлены 92 из 100 пар (`artifacts/attempt-14-before-http.json`).

Теперь ожидание соединения ограничено 5 секундами. Весь вызов процессора,
включая чтение, запись и повтор после разрыва Neon, имеет асинхронный бюджет
7 секунд. При истечении API закрывает обработку ответом 429 с `Retry-After: 1`,
не возвращая исходный текст. Это оставляет запас на доставку ответа, но не
гарантирует внешний SLA: холодный запуск платформы и сеть вне обработчика,
а синхронные участки не могут быть прерваны `asyncio.timeout` немедленно.
Постоянные 429 также не являются успешным прохождением нагрузки.

Три новых теста проверяют зависшее чтение, потерю подтверждения уже сохранённой
записи и отмену клиентом. После таймаута освобождается место в ограничителе
параллельных запросов. Повтор оригинала возвращает маску, а повтор этой маски
восстанавливает оригинал точно; дополнительной записи не возникает.

Локально: 90 pytest-тестов пройдены, один live-тест PostgreSQL пропущен;
Ruff и `git diff --check` пройдены. В первом общем прогоне существующий тест
плотного длинного текста получил regex-таймаут 0.1 с. Отдельный повтор теста
и повтор полного набора прошли. Детектор и порог regex в этом изменении не
менялись; чувствительность к задержкам выполнения остаётся ограничением.
